# Agent questions, `@file:` attachments and prompt watchdog

The PR makes the extension advertise `_meta.kiro.userInput`, so the engine asks questions through `_kiro/userInput` instead of a permission request with only "Allow" options. Both UIs get a question prompt (webview card, terminal numbered prompt). `@file:path` mentions are expanded into `<attached_file>` blocks inside `AcpClient.prompt`, so both UIs share the code. A watchdog cancels a turn that gets no engine event for 10 minutes. Question parsing and file expansion are pure modules with unit tests, and the fake-engine tests cover the protocol paths.

Watch for: `@file:` reads any absolute or `~/` path with no feedback to the user when it attaches or skips (likely); question identity falls back to an empty `toolCallId` and then collides in `ChatSession` and the webview (possible); the "turn may be stuck" log fires while the user is just reading a question (confirmed, cosmetic).

**Verdict**: APPROVED

## High-level view

Questions are tracked in `AcpClient` by JSON-RPC id and surfaced as `question` / `questionResolved` events. Every exit path (answer, cancel, end of turn) removes the pending entry and tells the UIs, so no card is left behind. The answer is sent before `session/cancel`, so the engine isn't left waiting.

`@file:` expansion is deliberately conservative on size and type (256 KB per file, 1 MB per prompt, no NUL bytes). Its weak point is visibility: skips only go to the output channel, and attaches are not shown at all. It also follows symlinks and has no workspace boundary.

The watchdog arms per prompt, disarms on the first `session/update` or server request, and then only logs. A question or approval counts as activity when it arrives, but the quiet-turn log doesn't know the user is the one being waited on.

<summary>Issues (5)</summary>

1. **Silent `@file:` outcomes** (likely) — A skipped mention (typo, too large, binary) only reaches the output channel and the agent receives the literal text. Show a short system line in both UIs listing attached and skipped files.
2. **No boundary on `@file:` paths** (possible) — `~/` and absolute paths are read, and `statSync` follows symlinks. A pasted prompt containing `@file:~/.ssh/id_rsa` would be sent to the model. The TUI behaves the same, so this may be accepted. If so, say it in the README, or log every attach so it is at least visible.
3. **Empty `toolCallId` collisions** (possible) — `mapUserInput` uses `String(p.toolCallId ?? "")`. Two questions without an id overwrite each other in `ChatSession.pendingQuestions`, and `dropQuestionCard("")` removes every id-less card. Fall back to the JSON-RPC id when `toolCallId` is missing. Not verified whether the engine always sends one.
4. **Quiet-turn log during a question** (confirmed) — `lastEvent` only moves on engine traffic, so a user thinking for over 30 s produces "the turn may be stuck". Skip the quiet log while `pendingQuestions` or `pendingPermissions` is non-empty.
5. **Terminal Ctrl+C skips the question** (possible) — While a question is active, Ctrl+C is treated as "skip" instead of interrupting the turn, which differs from the usual Ctrl+C. Check this matches the TUI.

### Question lifecycle across AcpClient, ChatSession and the UIs

```
engine --_kiro/userInput--> AcpClient.pendingQuestions[id]
                              |  event: question
                              v
                  ChatSession.pendingQuestions[toolCallId] -> webview card
answer -> answerQuestion(id) -> response {answered|dismissed}
cancel() -> dismissed, then session/cancel
prompt finally -> dropQuestions(false) -> questionResolved
```

Two keys are used for the same question: the JSON-RPC id in `AcpClient` and the terminal, `toolCallId` in `ChatSession`, the transcript and the webview DOM. `mapUserInput` defaults a missing `toolCallId` to `""`, so for an id-less question the second map and the DOM selector can't tell questions apart. Using `String(id)` as the fallback keeps the UI keys unique.

If the user answers after the engine already cancelled, `handleQuestionAnswer` ignores it. The webview has already replaced the card with "You answered: …", so the user believes it was delivered. This is a narrow race and low impact.

### `@file:` expansion visibility and reach

`expandFileMentions` runs inside `prompt()`, after `runStarted`. Attached files appear in the prompt only (`displayText` keeps the chat showing what was typed), so the user has no confirmation of what the model received. Skips are emitted as `log` only. A mistyped `@file:src/foo.tx` therefore looks like it worked. The path is not restricted to the workspace, and `~/` and absolute paths are accepted. The prompt is user-typed, so this matches the TUI, but pasted text can carry a mention the user doesn't notice. The file text is also placed inside the tag without escaping the `path` attribute or a literal `</attached_file>` in the content. This only matters for the model's reading of the prompt, not for extension safety.

### Watchdog and quiet-turn log

`failed` rejects after 10 minutes of silence and `cancel()` is called first, so a late `cancelled` response is harmless. Only `session/update` and server requests call `onActivity`; other engine notifications don't, so a turn that only sends non-`session/update` notifications for 10 minutes would be cancelled. Probably rare. The quiet log uses `lastEvent`, which doesn't change while the user answers a question or approval, so a slow answer logs a misleading "may be stuck" line.

### Test coverage

Covered: question parsing and limits, `@file:` expansion rules, capability sent on `initialize`, answer and cancel paths, `displayText`, watchdog fire and disarm, the terminal prompt, and end-to-end terminal turns. Not tested: the webview card and its restore after reload (the PR notes this and adds TEST.md steps), the empty `toolCallId` case, symlinked files, and the quiet-turn log while a question is pending.
